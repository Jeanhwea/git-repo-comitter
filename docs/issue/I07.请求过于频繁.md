# I07. 请求过于频繁（429 限流）需求整理

> 原始现象（复现）：
>
> ```
> $ grc
> 正在生成提交信息...
> 意外错误: 429 请求过于频繁，请稍后再试
> ```

## 1. 背景

grc（Git Repository Committer）在生成提交信息、批量提交、文件审查等环节都依赖大模型（LLM）的 API 调用（OpenAI 兼容协议）。`grc` 命令触发的「生成提交信息」即通过 `src/infra/llm/transport/client.ts` 的 `chatCompletion` 向配置的 `endpoint` 发请求。

调用大模型的服务端普遍对请求频率（RPM/TPM）设有限制。当短时间内请求过多、或上游（如网关/代理）主动限流时，会返回 **HTTP 429**，并通常带有 `Retry-After` 头表示需等待的秒数。429 是一种**瞬时、可恢复的**错误，语义上应当「等待后重试」，而不是当作致命错误直接终止。

## 2. 现状

- `src/infra/llm/retry.ts` 的 `callWithValidation` 已实现一层重试，但**只对「格式校验失败」重试**：`MAX_RETRIES = 3`，每次校验不通过就追加 `repairHint` 让模型重新生成。
- 对传输层异常，`chatCompletion` 没有任何捕获：429 由 OpenAI SDK 直接抛成 `APIError` 异常，向上冒泡。
- `src/app/cli/program.ts:48` 的兜底捕获把它当成未知错误打印：

  ```ts
  console.error("意外错误:", err instanceof Error ? err.message : String(err));
  ```

  于是用户看到的就是 `意外错误: 429 请求过于频繁，请稍后再试`。
- 现有 `GrcErrorCode`（`src/shared/errors.ts`）**没有**针对限流的稳定错误码，无法被调用方（CLI / 库）按类型分支处理。

结论：**当前根本没有对 429 做任何分类、退避或重试**，只是把 SDK 的原始报错兜底打印出来，并套上一层「意外错误」前缀。

## 3. 差距

| #   | 差距                                | 影响                                               |
| --- | ----------------------------------- | -------------------------------------------------- |
| G1  | 429 未被识别为「可重试错误」，直接逃逸为「意外错误」 | 一次限流就整轮失败，用户体验差                     |
| G2  | 无退避（backoff），未利用 `Retry-After`        | 立即重试大概率继续被限流                           |
| G3  | 限流重试与「格式校验重试」混用同一计数器/循环     | 语义不清；限流不应追加 `repairHint`                |
| G4  | 无面向用户的友好提示（如「等待冷却 N 秒…」）      | 用户不知道发生了什么、要不要重试                   |
| G5  | 无稳定错误码（如 `RATE_LIMITED`）             | 库调用方无法据此分支，CLI 也无法给出针对性退出码   |
| G6  | 批量生成（`batch.ts`）连续多轮调用无主动节流     | 更容易触发 429，且重试会雪崩                       |

## 4. 路径（提案）

建议把限流处理收敛在已有的「唯一收敛点」`callWithValidation`，与「校验重试」解耦：

1. **错误分类**：在 `chatCompletion` 或 `callWithValidation` 入口，识别 SDK 抛出的 `APIError`：
   - `status === 429` → 可重试（限流）；
   - `status === 500/502/503` 或网络超时 → 可重试（可选，见开放问题）；
   - 其余（如 401/403 配额、4xx 参数错误）→ 不可重试，直接抛出 `GrcError`。
2. **独立退避重试**：新增一个**限流重试计数器**（如 `MAX_RATE_LIMIT_RETRIES`），与 `MAX_RETRIES`（校验重试）分开；命中 429 时不追加 `repairHint`，仅 `await sleep(backoff)` 后原样重发。
3. **退避策略**：优先读取响应 `Retry-After`（秒）；缺失时退化为指数退避（如 1s、2s、4s，带上限）。
4. **进度反馈**：重试前 `emitProgress` 打印 `等待限流冷却 N 秒（第 k/m 次）…`，让用户有预期。
5. **稳定错误码**：在 `GrcErrorCode` 增加 `RATE_LIMITED`；限流重试耗尽后抛 `GrcError("请求过于频繁，请稍后重试或降低批量规模", "RATE_LIMITED")`，CLI 出口据此给出清晰文案与退出码，不再走「意外错误」兜底。
6. **批量侧节流（可选增强）**：`batch.ts` 在多轮生成之间加入最小间隔 / 令牌预算感知的节流，从源头降低 429 概率。

> 架构约束提醒：限流重试属于 LLM 基础设施职责，**不应引入 prompts 依赖**（与 I06 的 `repairHint` 传入式设计保持一致，避免 infra → prompts 回边）。

## 5. 开放问题

- **Q1 放置位置**：限流重试放在 `chatCompletion`（传输层）还是 `callWithValidation`（重试层）？前者对全部调用方透明，后者复用现有收敛点。倾向后者，但需确认不会与校验重试互相干扰。
- **Q2 作用范围**：429 处理是否一并覆盖 `file-review/reviewer.ts`、`commit-message/batch.ts`、`generator.ts`？三者都走 `callWithValidation`，改一处即可全收，但需回归验证。
- **Q3 5xx / 超时是否同路径**：是否把 5xx 与网络超时也纳入退避重试？还是仅限 429？
- **Q4 重试上限与是否可配**：限流重试次数 / 最大等待要不要做成用户配置？默认值多少（如 3 次 / 累计 ≤ 30s）？
- **Q5 批量节流粒度**：`batch.ts` 是否需要在调用之间主动 sleep / 限速？阈值如何定？
- **Q6 错误文案**：限流耗尽时，文案是建议「稍后重试」还是「降低批量规模 / 更换模型 / 调高配额」？

## 6. 结论

429 限流当前被当作「意外错误」直接抛出，缺少分类、退避与重试，是明确的功能缺口（G1–G6）。推荐方案：**在 `callWithValidation` 这一唯一收敛点增加独立的限流重试分支**——识别 429 → 读 `Retry-After` 或指数退避 → 原样重发 → 耗尽后抛稳定码 `RATE_LIMITED` 并由 CLI 给出友好提示；批量生成侧可再加主动节流作为增强。该方案改动集中、不改现有架构约束，建议作为 I07 的落地范围。
