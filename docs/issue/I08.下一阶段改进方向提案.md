# I08. 下一阶段改进方向提案

## 0. 摘要

对 `dev`（`938da48`，v1.3.6）做完代码、测试、构建、文档四路审查后的核心判断：

> **这个项目不缺设计，缺的是「让设计无法被绕过」的自动化约束。**

分层架构执行得相当好——全仓未发现跨层 import、循环依赖或纯核里的 Node 专有 API，三入口契约也基本落实。因此**不建议做架构级重构**。真正让缺陷持续积累的是三件事：CI 不跑测试、CI 构建与发布构建不是同一条链、以及「校验是写入 git 前最后一道关」这句规格在兜底路径上被绕开。

建议的推进顺序是：**先补门禁（W1）→ 再封死提交旁路（W2）→ 然后把规则与阈值收敛成单一来源并自动对账（W3）→ 接着加固 LLM/git 调用链（W4）→ 最后才处理上下文保真、文档时态与大文件拆分（W5/W6）**。理由见第 5 节：前四项都是「防止下一处缺陷产生」的基础设施，放在重构之前收益最高。

本文只做评估与提案，**不改任何源码**；每条发现标注证据位置，并对「事实」与「待验证推测」作了区分。

### 3.2 P0｜提交前最后一道关存在旁路（已实证）

这是本次评估中**唯一会造成错误结果写入 git 历史**的问题，优先级最高。

- **规格冲突**：`docs/feat/F04.提交消息严格校验.md:155` 要求「重试耗尽必须中止，不得带着不合规的消息执行 `git commit`」，`:174` 要求「任何绕过校验直接提交的通路都不允许存在」；而 `docs/feat/F06:103-117` 要求降级兜底继续提交。实现选择了 F06：`src/domain/commit-flow.ts:250-266` 捕获 `VALIDATION_FAILED` / `LLM_FAILED` 后取兜底消息，`:274-276` 无条件 `gitCommit`。**F04 的单点防护事实上已失效，两份规格未裁决谁优先。**
- **兜底自身不合规仍返回**：`src/domain/commit-message/fallback.ts:292-317` 在校验失败时只 `log.warn("…已修正")`，仅当要点数 `> MAX_BODY_BULLETS * 2`（20）才截断；阈值 10 与 20 不一致，其它失败原因（标题超长、C4 等）原样返回。`buildBody()`（`:202-223`）用「分组行 + 每文件一行」计数，校验器 `checker.ts:294-298` 对 `trim()` 后以 `- ` 开头的行全部计入要点。

**实证**（`tmp/proposal-verify.ts`，构造 ChangeSet 直接调用两个函数）：

| 变更规模          | 生成要点数     | `validateCommitMessage`                                           | 日志                                     |
| ----------------- | -------------- | ----------------------------------------------------------------- | ---------------------------------------- |
| 3 新增 + 2 修改   | 7              | `valid=true`                                                      | —                                        |
| 5 新增 + 5 修改   | 12             | **`valid=false`：`[C3] 正文要点数量不得超过 10 条 (当前 12 条)`** | `WARN …未通过校验，已修正`（实际未修正） |
| 8 新增 + 8 修改   | 18             | **`valid=false`：`[C3] …当前 18 条`**                             | 同上                                     |
| 12 新增 + 12 修改 | 26 → 截断到 20 | **`valid=false`：`[C3] …当前 20 条`**                             | 同上，截断后仍不合规                     |

即：**一次包含 10 个文件的普通降级提交，就会把未通过校验的消息直接写入 git**。这个结论不依赖推测，是可复现的。

- **CLI / 库行为分叉**：`src/app/commands/commit.ts:29-34` 在 `apiKey` 为空时直接抛 `CONFIG_MISSING`，使 F06 P1 兜底对 CLI 完全不可达；而库的 `executeCommit`（`commit-flow.ts:185-197`）会在同样条件下兜底并提交。README:163、S01:185 所称「两者不会出现两套行为」不成立。
- **凭据暴露面**（并非日志泄露，日志只打 endpoint/model）：`src/config/user-file.ts:53-56` 明文写 `~/.grc/config.json` 且 `writeFileSync` / `mkdirSync` 均未指定 `mode`（常见 0644）；`src/app/cli/input.ts:10-15` 用 `readline.question` 让 `grc init` 的 API Key **明文回显终端**。`app/config/load.ts:36-44` 的自动修复回写同样不收紧权限。

### W2 · 封死「写入 git 前的旁路」（P0）

> **实施状态：已完成**（2026-11-16）。Q1 裁决为「保留离线降级，但降级消息必须合规，否则中止」；Q2 裁决为「CLI 与库在 apiKey 为空时行为一致，均允许规则化提交」。`commit-flow.ts` 新增统一 `commitChecked` 门禁，四条路径共用；`fallback.ts` 改为按主题归并、三级退化（完整消息 → 仅标题 → 中止）；配置写入收紧至 0600/0700，`grc init` 的 API Key 不回显。F04 / F06 已同步裁决。验证：新增 16 个用例，`pnpm check` / `pnpm lint` / `pnpm test`（43/43）/ `pnpm build` 通过。

1. **先裁决规格**：F04「重试耗尽必须中止」与 F06「降级后继续提交」二选一，写成唯一准绳（开放问题 Q1）。无论选哪条，都要保证**任何进入 `gitCommit` 的消息都经过 `validateCommitMessage` 且 `valid === true`**。

## 5. 优先级与依赖

| 顺序 | 工作包          | 优先级 | 为什么排在这里                                                         |
| ---- | --------------- | ------ | ---------------------------------------------------------------------- |
| 1    | W1 质量门禁     | P0     | 后续每个改动都需要「改坏了能被发现」的前提；且改动面最小、收益立刻可见 |
| 2    | W2 提交旁路     | P0     | 唯一会污染 git 历史的问题，已实证；修完要能被 W1 的测试锁住            |
| 3    | W3 规则对账     | P1     | 把 W2 的一次性修复变成长期不漂移的机制，依赖 W2 确定的唯一准绳         |
| 4    | W4 链路健壮性   | P1     | 影响失败时的体验与可诊断性，不影响成功路径正确性                       |
| 5    | W5 契约文档收敛 | P1     | 可与 W3/W4 并行穿插做，成本低，主要消除调用方误用                      |
| 6    | W6 上下文与拆分 | P2     | 行为变更面最大、收益偏「质量」而非「正确性」，有测试网后再做           |

一句话：**先让仓库有能力发现自己坏掉，再修已经坏掉的地方，最后才优化还不太好的地方。**

## 6. 建议的验收基线

可作为各工作包完成后的共同 Definition of Done：

1. `ci.yml` 与 `publish.yml` 使用同一条 `pnpm build` 链，且 CI 执行 `pnpm test` + coverage。
2. F04 的 T01–T20 全部有单元测试；`checker.ts`、`fallback.ts`、`diff/split.ts` + `budget.ts`、`commit-flow.ts`、`program.ts`（用现成的 `runGrc({ argv })`）、`config/user-file.ts` 六条关键路径不再是零覆盖。
3. 任何调用 `gitCommit` 的路径都能被一条「校验未通过即不提交」的测试证明。
4. 规则对账脚本零差异；`shared/commit-limits.ts` 是全部阈值的唯一来源。
5. tag 与 `package.json.version` 不一致时发布被阻断。
6. `pnpm check` / `pnpm lint` / `pnpm test` / `pnpm build` 在干净环境一次通过。

## 9. 结论

dev 当前是一个**设计文档完备、分层执行到位，但自动化约束不足**的项目。24 篇文档把意图写得很清楚，可 CI 不跑测试、发布不设门禁、规则编号靠人工对账，于是「已实现」的文档和真实行为之间持续漂移，最典型的后果就是 3.2 节实证的那条：兜底消息未通过 F04 校验，却仍被写入提交历史。

建议以 **W1（门禁）→ W2（正确性）→ W3（机制化）** 为第一阶段，W4/W5 穿插进行，W6 待测试网成型后再启动。第一阶段完成后，这个仓库才具备「文档写下的约束不会被下一次改动悄悄破坏」的能力。
