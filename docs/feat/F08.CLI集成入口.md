# CLI 集成入口

原始需求（一句话）：参考 `src/cli.ts`，提供一个 CLI 接入的一键入口函数。

---

## 背景

grc 当前对外有三种「接入面」，各自服务不同的宿主：

- **库入口** `src/lib.ts` —— 对外承诺的精简公共 API（生成、校验、配置、错误模型），供其他代码以编程方式调用（F05）；
- **浏览器入口** `src/lib-browser.ts` —— 纯函数侧 API，供 Tauri WebView / Next.js 浏览器端使用，不装配 git 执行器（F07 浏览器适配）；
- **CLI 入口** `src/cli.ts` —— 产出带 shebang 的 `dist/cli.cjs`，承接 `grc` / `git-repo-comitter` 命令。

但凡要把 grc 的「整条命令行能力」嵌进另一个 **Node 宿主进程**（例如另一个 Node CLI 工具、一个以编程方式驱动 `grc` 的测试 / 脚本、或一个在 Node 侧而非 WebView 侧拉起 grc 的桌面应用）时，现状都不够顺手：

- 现在 CLI 的启动逻辑被硬编码在 `src/cli.ts` 模块顶层，是「副作用式执行」——import 即触发 `setupNodeGitExecutor()` 与 `runCli()`，没有可供宿主显式调用的收敛入口；
- 宿主若想自己接管，必须分别拼装「装配 Node 执行器」与「运行 program」两件事，二者分散且极易漏掉装配那一步——历史上 CLI 入口漏装就报过「git 执行器未装配」（见 F07 浏览器适配 §6 的约定 E1）。

核心诉求：**把「装配 + 运行」收敛为一个可被宿主稳定调用的一键入口函数**，让 CLI 既能保持 `grc` 命令的 bin 形态，又能被 Node 宿主以函数形式接入。

---

## 现状

代码层面已经具备「一键入口」的零件，只是尚未组合、未对外暴露：

- `src/cli.ts`（共 18 行）：模块顶层直接 `setupNodeGitExecutor(); runCli();`，**没有任何导出函数**；其注释已点明与 `lib.ts` 并列、命名 `cli.ts` 是为了避免与库产物 `dist/index.*` 语义混淆。
- `src/app/cli/program.ts`：
  - 导出 `runCli(): void`，内部 `program.parse(process.argv)`；
  - 负责命令注册（`init` 子命令 + 默认 `commit` 动作）、全局选项（`-s/--staged-only`、`-v/--version`、`--verbose`、`--debug`、`--trace`）、日志级别（`applyLogLevel` 经 `preAction` hook 统一应用）、以及统一错误出口 `handleCliError`；
  - `handleCliError` 实现「架构 A4」原则：错误码由领域层给出，**退出码翻译只发生在 CLI 出口这一处**，所有 `GrcError` 统一映射到 `EXIT_CODES`。
- `src/node/setup.ts`：导出 `setupNodeGitExecutor()`，把基于 `child_process` 的默认执行器注册进 `GitExecutor` 端口（`setGitExecutor(childProcessExecutor)`）；浏览器 / WebView 入口不调用本函数。
- `src/lib.ts`（库入口）：同样在加载时 `setupNodeGitExecutor()`，并对外承诺「不读写 `~/.grc`、不打印、不 `process.exit`、失败抛 `GrcError`」的纯净契约。

一句话总结：装配函数、运行函数都已存在且职责清晰，**缺的只是一个把两者组合并对外暴露的「一键」包装**。

---

## 差距

1. **无显式一键入口**：CLI 的「装配 + 运行」散落在 `cli.ts` 顶层，宿主想接入只能手动复刻这两步，没有 `runGrc(...)` 之类的单一调用点。
2. **import 即触发副作用**：`cli.ts` 顶层直接执行，任何 `import` 都会无条件跑掉装配与 `runCli`，违背「入口不应有隐含副作用」的契约，也无法在测试 / 嵌入场景里控制时机。
3. **`runCli` 不支持自定义 argv**：当前 `program.parse(process.argv)` 直接吃进程参数，宿主无法在嵌入时喂入自己的参数（例如测试里传入 `["commit", "--staged-only"]`），也难以作为函数返回值拿到结果。
4. **装配与运行耦合、易漏装**：两件事分离，历史教训是「忘了装配就报 git 执行器未装配」；缺少一处强制约定来保证「只要走 CLI 入口就一定装配」。
5. **返回值 / 错误模型不统一**：CLI 走 `void + process.exit`，库走「抛 `GrcError`」，宿主若以编程方式接入，没有一致的「成功 / 失败 / 错误码」约定可依赖。
6. **与其他两个入口的关系未写明**：`cli.ts` 与 `lib.ts` 共用 `setupNodeGitExecutor`，但三者（CLI / 库 / 浏览器）的「谁负责装配、谁负责退出码、何时注入执行器」职责边界，目前只在散落注释里，没有成文约定。

---

## 路径

### 核心思路：抽一个 `runGrc` 一键入口，cli.ts 退化为薄壳

把「装配 + 运行」从 `cli.ts` 顶层搬进一个显式函数，由它统一负责顺序装配与运行；`cli.ts` 顶层只保留一个 `runGrc()` 调用，以维持 `dist/cli.cjs` 的 bin 行为。

**P1 —— 新增一键入口函数（基础）**

在 `src/cli.ts` 暴露显式入口，内部顺序组合「装配 Node 执行器 → 运行 program」：

```ts
import { runCli } from "@/app/cli/program";
import { setupNodeGitExecutor } from "@/node/setup";

export interface RunGrcOptions {
  /** 自定义参数；缺省回落到 process.argv，便于嵌入与测试。 */
  argv?: string[];
}

export function runGrc(options: RunGrcOptions = {}): void {
  // 强制装配：只要走 CLI 入口，就一定注册 child_process 执行器（约束 E1）。
  setupNodeGitExecutor();
  runCli(options.argv);
}
```

同步把 `src/app/cli/program.ts` 的 `runCli` 改为可注入 argv：

```ts
export function runCli(argv: string[] = process.argv): void {
  program.parse(argv);
}
```

**P2 —— cli.ts 退化为 bin 薄壳**

```ts
// 仅作为 dist/cli.cjs 的可执行入口；其余宿主改用 runGrc()。
runGrc();
```

这样 `grc` 命令行为完全不变，而 Node 宿主 / 测试可直接 `import { runGrc } from "git-repo-comitter/bin"`（或内部路径）后 `runGrc({ argv })` 调用，import 不再有隐含副作用。

**P3 —— 错误出口收敛（延续 A4）**

`runGrc` 内部不自行翻译退出码，继续复用 `program.ts` 的 `handleCliError` 语义，确保「错误码 → 退出码」只在 CLI 出口一处翻译；若将来要让宿主以编程方式感知结果，再在 P4 讨论返回值形态。

**P4 —— 成文约定（可选）**

在 `src/cli.ts` / `docs/spec` 里补一条「CLI 入口契约」：明确装配职责（`cli.ts` 与 `lib.ts` 都走 `setupNodeGitExecutor`）、argv 来源、退出码模型，并把「一键入口」与 `lib.ts`（库）、`lib-browser.ts`（WebView）的职责边界写清。三者分工已厘清：浏览器入口归属 F07，本篇 CLI 一键入口归属 F08，库入口 `lib.ts` 另列 F05，互不混用。

---

## 开放问题

1. **返回值形态**：保持 `void + process.exit` 的经典 CLI 语义，还是改为 `Promise<number>`（返回退出码）/ 抛出 `GrcError`，以更契合库式 / 宿主式集成？倾向「默认 `void`，但 `runCli` 可返回退出码」的折中，避免破坏既有 bin 行为。
2. **argv 注入粒度**：`runGrc` 仅接受 `argv: string[]` 是否够用？宿主是否还需要覆写 `program` 实例（追加子命令、注册 hook）？倾向本期只接受 argv 数组，保持接口最小。
3. **执行器装配幂等性**：若宿主在调用 `runGrc` 前已 `setGitExecutor` 注入了 Tauri IPC 等非 `child_process` 实现，重复 `setupNodeGitExecutor()` 应覆盖还是跳过？倾向「CLI 入口总是强制覆盖为 Node 默认」——因为 CLI 的语义就是 Node 环境，不该被宿主注入污染；需要注入的场景应直接走 `lib.ts` / `lib-browser.ts`。
4. **导出位置**：`runGrc` 是否要沉淀进对外 `exports`（如 `git-repo-comitter/bin`），还是仅作为内部 / Node 工具函数？若对外，需同步更新 `package.json` 的 `exports` 与类型产物。
5. **测试与 bin 兼容**：引入显式入口后，如何兼顾 `npm bin` 调用与单元测试——确保 `import` 不再自动运行，且 `runGrc({ argv })` 可在 CI 内无 TTY、无真实 git 的情况下演练？

---

## 结论

F08（CLI 集成入口）的本质不是新增能力，而是**把已经存在、但散落在 `cli.ts` 顶层的「装配 + 运行」收敛为一个对外暴露的一键入口函数 `runGrc`**，并让 `cli.ts` 退化为维持 bin 行为的薄壳。

- **核心收益**：消除「import 即运行」的隐含副作用；给 Node 宿主 / 测试一个稳定、可注入 `argv` 的调用点；用一处强制约定杜绝「漏装 git 执行器」的历史问题。
- **关键约束**：不破坏 F05 的库契约与 A4「退出码只在 CLI 出口翻译」原则；执行器装配须与 `lib.ts` 的 Node 入口保持一致。
- **推荐落点**：先完成 P1（新增 `runGrc` + 让 `runCli` 可注入 argv）+ P2（cli.ts 薄壳化），工作量约半天；P3 / P4 作为加固项按需推进。
