# 抽象成库提供接入

## 背景

grc 当前是一个基于 LLM 的 Git 提交信息生成命令行工具，发布到 npm 后以 `grc` 命令使用。

但「生成提交信息」与「执行提交」这两件事本身是有复用价值的原子能力，很多场景并不想启动一个子进程、或依赖全局 `~/.grc` 配置：

- 编辑器插件（VS Code / JetBrains）想在保存或提交前内联生成提交信息；
- Git 钩子（prepare-commit-msg / pre-commit）想调用生成逻辑；
- CI 流水线想以编程方式生成规范提交信息而不输出到终端；
- 其他 AI Agent / 工具想复用 grc 的 diff 收集、消息校验、分批合并能力。

核心诉求（原始需求一句话）：**可以作为一个库，被其他的代码调用**。

## 现状

代码层面已经具备抽库的基础：

- 已按应用 / 配置 / 领域 / 基础设施 / 提示词 / 共享分层（`src/app`、`src/config`、`src/domain`、`src/infra`、`src/prompts`、`src/shared`）；
- 领域层与基础设施层多数函数签名已相对独立，例如 `generateCommitMessageBatched(diff, config)`、`validateCommitMessage`、`getStagedDiff()`、`gitCommit(message)`、`loadConfig()`；
- `package.json` 已声明 `bin: grc`，构建用 Vite `lib` 模式产出 `dist/index.cjs`。

但当前形态本质是「CLI 包」而非「可被调用的库」：

| 维度 | 现状 | 问题 |
|------|------|------|
| 入口 | `src/index.ts` 仅 `runCli()` | 没有库入口，也没有导出任何 API |
| 产物 | 单文件 `dist/index.cjs`，带 `#!/usr/bin/env node` shebang | 是 CLI 打包产物，不是可消费的模块 API |
| 包描述 | `main: dist/index.cjs`，无 `exports` 字段 | 消费者无法 `import { ... } from "git-repo-comitter"` |
| 关注点泄漏 | 领域层 `batch.ts` 直接 `console.log` 进度；`config/loader.ts` 硬编码 `~/.grc/config.json` 并含交互式 `question()` 修复 | 库消费者无法控制输出、会被全局配置与 TTY 交互绑架 |
| 错误处理 | `program.ts` 用 `CliError` + `process.exit` 收口 | 库不应调用 `process.exit`，应抛出领域错误由调用方决定 |
| 类型产物 | 未生成 `.d.ts` | TypeScript 消费者无类型提示 |

## 差距

1. **无库入口与导出面**：没有 `exports` 映射，没有命名导出，消费者无法以编程方式引用任何能力。
2. **产物形态不匹配**：当前单文件 CLI 打包（含 shebang）无法作为模块被 `require`/`import` 后干净使用。
3. **CLI 关注点泄漏进领域层**：`console.log` 进度、`~/.grc` 全局配置、交互式修复、TTY 交互。库必须可注入配置、可静默、不触发终端交互。
4. **无配置注入点**：`loadConfig()` 默认读全局文件，无法传入纯对象配置；默认值未单独导出供复用。
5. **无可控输出 / 日志**：用户态输出散落 `console.log`，库应提供 logger / 输出槽注入或默认静默。
6. **错误模型偏 CLI**：`CliError` 带 `exitCode` 并触发 `process.exit`；库应抛可捕获的领域错误，CLI 适配器再翻译成退出码。
7. **无公共 API 契约**：未界定哪些函数稳定公开、哪些仅内部使用，也无类型声明产物。

## 路径

**P1 —— 定义库入口与导出面（基础）**

- 新增 `src/lib.ts` 作为库入口，汇聚「稳定公共 API」的命名导出；
- 在 `package.json` 增加 `exports` 字段，区分 `import`/`require` 指向库构建产物，保留 `bin` 给 CLI；
- 调整构建：用 Vite 额外产出库 artifact（建议 ESM + CJS 双格式）并生成 `.d.ts`。

**P2 —— 解耦 CLI 关注点（关键）**

- 把 `batch.ts` 中的 `console.log` 进度改为走 `shared/logger` 或 `onProgress?` 回调；
- 让 `loadConfig()` 接受可选的显式 `AppConfig`，将「读全局文件」下沉为独立 `loadUserConfigFile()`，库默认不读全局配置；
- 把 `offerRepair` 等交互式修复改为「返回校验错误」而非主动 `question()`，避免库触发 TTY 提示；
- 把 `CliError` + `process.exit` 收敛为领域错误，CLI 适配层负责翻译成退出码。

**P3 —— 确立公共 API 契约**

- 明确导出：`generateCommitMessage`、`generateCommitMessageBatched`、`validateCommitMessage`、`getStagedDiff`、`gitCommit`、`loadDefaultConfig`，以及编排函数 `commit({ repoPath?, config, stagedOnly?, onProgress? })`（返回结果对象而非打印/退出）；
- 内部实现保持不导出；在 README 增加「作为库使用」章节与示例。

**P4 —— 验收与兼容**

- 加单测覆盖库 API（不依赖真实 git / TTY）；
- 验证 `exports` 字段不破坏既有 `main` 解析的 CJS 消费者；
- 建议把 `grc` CLI 自身改为「库的参考消费者」，证明库能力闭环。

## 开放问题

1. 库产物形态：仅保留 CJS，还是补 ESM + `.d.ts`？倾向双格式 + 类型声明（发布包通行做法）。
2. 构建拆分方式：单 Vite 配置多 lib entry，还是独立 `vite.lib.config.ts`？
3. 单包还是拆包：沿用当前包同时承载 `bin` + `exports`，还是拆成 `git-repo-comitter`（库）与 `grc`（CLI）两个包？倾向单包两者并存，降低维护成本。
4. 配置默认值行为：库默认要求显式传入配置，还是为兼容回落到 `~/.grc`？倾向默认显式，全局文件作为可选的便捷入口（避免隐式全局副作用）。
5. 默认输出级别：默认静默还是 info？倾向默认 info 且可注入 logger 覆盖。
6. 稳定 API 边界：哪些 domain 函数纳入公共 API、哪些保持内部？需与现有 CLI / 测试共用同一套契约。
7. 版本号影响：新增 `exports` 字段可能改变部分 CJS 消费者的解析路径，是否需要 bump 主版本？建议先实测再判定（倾向 minor，除非实测破坏）。
8. 编排函数 `commit()` 是否作为库一等公民暴露，还是仅保留底层能力？

## 结论

grc 的代码结构（分层清晰、领域/基础设施函数签名独立）**已经具备抽库基础**，主要工作量集中在两处：

1. 增加库入口 + `exports` 映射 + 类型产物，让能力可被编程引用；
2. 把泄漏进领域层的 CLI 关注点（终端输出、全局配置、TTY 交互、`process.exit`）解耦为可注入点。

建议采用「单包双产物」方案：`grc` CLI 继续作为库的参考消费者，库暴露一组经过筛选的稳定公共 API，并以注入式配置 / 日志 / 错误模型替代硬编码的 CLI 行为。落地可先完成 P1 + P2（入口、导出、配置注入），再推进 P3（API 契约与文档）。
