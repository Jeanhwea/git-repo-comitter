# 提交消息严格校验

## 概述

提交消息由大模型生成，模型输出天然不稳定：可能给出多个候选、擅自加代码块围栏、把多条消息拼在一条里、用全角冒号、超出行宽限制。这些结果一旦直接写入 `git commit`，污染的是不可撤销的提交历史。

本需求定义**一条提交消息在写入 git 之前必须满足的全部约束**，以及不满足时的处置方式。核心原则：

> 提示词负责让模型写对，校验负责拦住没写对的。两者规则必须同源、口径一致，任何一条规则不允许出现「提示词里写了但没有兜底」的状态。

规范的完整定义参考 [Conventional Commits v1.0.0](https://www.conventionalcommits.org/en/v1.0.0/)。

## 范围

| 维度     | 说明                                                                 |
| -------- | -------------------------------------------------------------------- |
| 适用对象 | 最终写入 git 的提交消息：单批直接生成的结果、分批场景下的合并结果    |
| 适用对象 | 用户在交互环节手工输入或改写后的消息（同样按本文规则判定后方可提交） |
| 不适用   | 分批场景的中间草稿（见下方说明）                                     |
| 不适用   | 文件审查门禁的 JSON 结果（另有校验规则）                             |

中间草稿只要求能被后续合并阶段消费，**不要求**满足本文全部约束；但「单条性」「禁用围栏」「语言」三类约束同样适用，否则无法合并出正确结果。

## 格式约定

```text
<type>[optional scope][!]: <description>

[optional body]

[optional footer(s)]
```

| 字段          | 必填 | 说明                                                      |
| ------------- | ---- | --------------------------------------------------------- |
| `type`        | 是   | 变更性质，必须取自允许清单，见 A1                         |
| `scope`       | 否   | 影响范围（模块/子系统名），见 A3                          |
| `!`           | 否   | 破坏性变更标记，位于 `type`/`scope` 之后、冒号之前，见 A2 |
| `description` | 是   | 一句话变更摘要，见 A6~A8                                  |
| `body`        | 否   | 要点列表，与标题相隔一个空行，见 C 组                     |
| `footer`      | 否   | git trailer 脚注，见 D 组                                 |

## 校验规则

规则编号用于失败原因的回显，必须稳定，不得随实现调整而重排。

### A. 标题行

| 编号 | 约束                                                                                                                                   | 通过示例                         | 拒绝示例                                                                   |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------- | -------------------------------------------------------------------------- |
| A1   | `type` 必填，且必须取自允许清单 `feat` / `fix` / `docs` / `style` / `refactor` / `perf` / `test` / `build` / `ci` / `chore` / `revert` | `feat(cli): ...`                 | `feature(cli): ...`、`更新(cli): ...`                                      |
| A2   | `!` 只能出现一次，且必须紧贴冒号之前                                                                                                   | `feat(api)!: ...`                | `feat!: (api) ...`、`feat(api)! !: ...`                                    |
| A3   | `scope` 使用小写英文、连字符分词；禁止空格、禁止右圆括号；禁止空括号 `()`                                                              | `refactor(storage-layer): ...`   | `refactor(storage layer): ...`、`refactor(): ...`                          |
| A4   | `type`/`scope` 与 `description` 之间必须是**半角冒号 + 恰好一个半角空格**                                                              | `fix: 修复...`                   | `fix：修复...`（全角）、`fix:修复...`（缺空格）、`fix:  修复...`（多空格） |
| A5   | `!` 存在时，标题本身仍须完整可读，`!` 不替代任何语义                                                                                   | `feat(api)!: 移除旧版兼容`       | `feat(api)!:`（无描述）                                                    |
| A6   | `description` 非空，禁止以句号结尾                                                                                                     | `fix: 修复登录重定向丢失参数`    | `fix: `、`fix: 修复登录重定向丢失参数。`                                   |
| A7   | `description` 以动词开头（中文取动词原形），禁止「修改了」「更新了」「优化了」等无信息量措辞                                           | `perf: 缓存解析结果降低重复开销` | `perf: 优化了代码`                                                         |
| A8   | 标题行总长不超过 **78** 字符                                                                                                           | —                                | 超长时被要求压缩描述，禁止直接截断                                         |
| A9   | 语言与标点遵守 `language` 节：简体中文表达，标题冒号仍为半角                                                                           | `docs: 更新 README 安装步骤`     | `docs: update README`（整句英文）                                          |

### B. 单条性

| 编号 | 约束                                                      | 通过示例        | 拒绝示例                              |
| ---- | --------------------------------------------------------- | --------------- | ------------------------------------- |
| B1   | 一条消息只允许出现一个标题行                              | 单个标题 + 正文 | 正文中再出现一条 `type(...): ...`     |
| B2   | 禁止出现分隔线（`======`、`------` 等）形式的拼接痕迹     | 无              | `feat(a): x` + `======` + `fix(b): y` |
| B3   | 禁止以序号、候选标记、「方案一/方案二」等形式输出多个版本 | 一条结果        | `1. feat(a): x  2. feat(a): y`        |
| B4   | 多主题变更必须收敛为「一条标题 + 一组要点」，不得拆成多条 | 见下方示例 3    | 见 B1 反例                            |

多主题变更的正确写法：

```text
refactor(storage): 统一缓存键的生成逻辑

- 抽取 keyBuilder 替代各处硬编码
- 迁移 session 与 permission 模块至新接口
```

### C. 正文

| 编号 | 约束                                                                                             | 通过示例                      | 拒绝示例                            |
| ---- | ------------------------------------------------------------------------------------------------ | ----------------------------- | ----------------------------------- |
| C1   | 正文与标题之间必须相隔**恰好一个空行**，禁止用单个换行直接接正文                                 | 标题 + `\n\n` + 要点          | 标题 + `\n` + 要点                  |
| C2   | 要点必须以**半角连字符 + 空格 `- `** 开头并独占一行，禁止 `*`、`•`、数字序号、Markdown 标题/加粗 | `- 支持 CSV 与 JSON 两种格式` | `* 支持 CSV`、`**要点**`、`## 要点` |
| C3   | 要点数量不超过 **5** 条                                                                          | 3 条要点                      | 7 条要点                            |
| C4   | 正文每行不超过 **118** 字符（比标题宽松，需容纳文件名与模块名）                                  | 含路径的要点                  | 写成不换行的长段落                  |
| C5   | 标题已完整表达变更时必须省略正文，禁止为凑篇幅复述变更内容                                       | `chore(deps): 升级依赖版本`   | 标题 + 与标题同义的 3 条要点        |

### D. 脚注

| 编号 | 约束                                                                             | 通过示例                                       | 拒绝示例                                    |
| ---- | -------------------------------------------------------------------------------- | ---------------------------------------------- | ------------------------------------------- |
| D1   | 脚注必须是 git trailer 格式 `Token: value` 或 `Token #value`，与正文相隔一个空行 | `Refs: 3f7a1c9`                                | `参考提交：3f7a1c9`、`refs=3f7a1c9`         |
| D2   | 多个脚注逐行排列，禁止同行并列或加项目符号                                       | 两行 trailer                                   | `- Refs: 3f7a1c9`、`Refs: 3f7a1c9, 8b2d1e4` |
| D3   | 标题带 `!` 时，必须有 `BREAKING CHANGE: 影响说明` 脚注                           | 见下方示例                                     | 只有 `!` 无脚注                             |
| D4   | `revert` 必须在脚注中用 `Refs:` 给出被回退的提交哈希                             | `revert: 新增 --staged 参数` + `Refs: 3f7a1c9` | `revert: ...` 无 Refs                       |

破坏性变更写法：

```text
feat(api)!: 移除对 Node 6 的运行时兼容

- 放弃 Node 6 的兼容分支
- 启用 Node 6 不支持的语言特性

BREAKING CHANGE: 运行环境要求升级至 Node 8 及以上。
```

### E. 载体与语言

| 编号 | 约束                                                                                                                       | 通过示例                                     | 拒绝示例                                             |
| ---- | -------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- | ---------------------------------------------------- |
| E1   | 输出必须是纯文本，**首行即标题**，禁止 Markdown 代码围栏、禁止前后缀解释、禁止空行开头、禁止结尾多余空行                   | 直接以标题开头                               | ` ```text ` 包裹、结尾两个换行                       |
| E2   | 禁止 emoji、禁止中英混排句式                                                                                               | `feat(cli): 新增 --staged 参数`              | `🎉 feat: add feature`、`修复 login redirect 的 bug` |
| E3   | 以下代码标识符、文件名与路径、命令与参数、第三方库与框架名、协议与规范名、`type`/`scope`、trailer token 保留原文，禁止翻译 | `fix(diff): 修复 parseDiffBlocks 的错位问题` | `fix(差异): 修复解析差异块的错位问题`                |
| E4   | 禁止繁体字、方言与网络用语；正文描述使用中文全角标点，但 A4 的冒号例外                                                     | —                                            | `修複`、`yyds`                                       |
| E5   | 只写变更内容能明确支撑的事实，禁止推测动机、影响或尚未实现的计划                                                           | `- 移除已被 keyBuilder 取代的实现`           | `- 为后续支持多租户预留扩展点`                       |
| E6   | 整条消息不得为空，空内容按 F3 兜底输出                                                                                     | —                                            | 空字符串                                             |

### F. 边界场景

| 编号 | 场景                                 | 要求                                                                                             |
| ---- | ------------------------------------ | ------------------------------------------------------------------------------------------------ |
| F1   | 暂存的变更为空，或仅含空白与格式噪音 | 输出 `chore: 无实质变更`，禁止留空或自由发挥                                                     |
| F2   | 二进制文件变更（只知文件名）         | 依据文件名与路径推断意图（如 `chore(assets): 更新配图与字体资源`），禁止描述或臆测二进制内容     |
| F3   | 超大变更被折叠为「已省略具体差异」   | 只记录受影响的文件名，标题须体现「等」「多处」等范围词；禁止把「变更内容过大」等说明文字写入消息 |
| F4   | 分批合并时部分草稿因长度限制被丢弃   | 同上标题处理，禁止声称已覆盖全部变更                                                             |

## 判定层级

不同约束的可执行性不同，分级是为了明确「由谁把关」，避免把主观判断伪装成硬性规则。

| 层级                 | 含义                                                                 | 覆盖规则                                                                       |
| -------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| **L1 机器判定**      | 可用确定性规则判定，必须拦截；失败即触发重试，重试耗尽必须中止提交   | A1、A2、A3、A4、A5、A6、A8、B1、B2、B3、C1、C2、C3、C4、D1、D2、D3、D4、E1、E6 |
| **L2 语言/统计判定** | 可用启发式判定，允许作为告警而非硬拦截，但必须在日志与回显中给出提示 | A9、E2、E3、E4                                                                 |
| **L3 仅约束模型**    | 无法可靠机器判定，只由提示词约束，不参与拦截                         | A7、C5、E5                                                                     |

## 失败处置

| 环节         | 要求                                                                                                                   |
| ------------ | ---------------------------------------------------------------------------------------------------------------------- |
| 失败原因     | 必须指明命中的规则编号与具体位置（字段名、行号、当前值 / 上限值），禁止只说「格式错误」                                |
| 一次命中多条 | 一次性列出全部命中项，禁止逐条迭代修复，避免反复重试                                                                   |
| 重试         | 携带失败原因重新请求模型，重试次数上限 **3** 次（含首次尝试）                                                          |
| 重试耗尽     | 必须中止，不得带着不合规的消息执行 `git commit`                                                                        |
| 终态输出     | 中止时输出命中的规则清单，并把最后一次生成结果原样展示给用户，便于人工判断；若存在交互环节，允许用户手动改写后重新校验 |
| 可观测性     | 每次重试的原因必须同时进入 debug 日志与用户可见输出，格式为「命中规则 + 具体值」                                       |

错误样例：

```text
提交信息格式校验未通过（第 1 次）:
  - [A4] 标题分隔符必须是半角冒号加一个空格，当前为 "fix:修复..."（实测 0 个空格）
  - [C4] 正文第 2 行 142 字符，超过上限 118 字符
正在重新生成...
```

## 一致性要求

| 要求             | 说明                                                                                    |
| ---------------- | --------------------------------------------------------------------------------------- |
| 规则同源         | 同一条规则不得在多处各写一遍；阈值（78 / 118、type 清单、要点上限 5）必须来自同一份定义 |
| 提示词与校验对齐 | 提示词里写出的每一条强约束，必须在本文规则清单中有对应编号，且标注其判定层级            |
| 单点防护         | 校验是写入 git 前的最后一道关，任何绕过校验直接提交的通路都不允许存在                   |
| 编号稳定         | 规则编号与 Failed reason 绑定，调整实现不改变编号语义                                   |

## 验收用例

| 编号 | 输入（标题行摘录）                                | 期望                                            |
| ---- | ------------------------------------------------- | ----------------------------------------------- |
| T01  | `feat(cli): 新增 --staged 参数用于仅提交暂存内容` | 通过                                            |
| T02  | `feature(cli): 新增参数`                          | 拒绝 A1，原因指出 `feature` 不在清单内          |
| T03  | `fix：修复登录问题`                               | 拒绝 A4，原因指出使用了全角冒号                 |
| T04  | `fix:修复登录问题`                                | 拒绝 A4，原因指出缺半角空格                     |
| T05  | `refactor(storage layer): 收敛键生成逻辑`         | 拒绝 A3，原因指出 scope 含空格                  |
| T06  | `refactor(): 收敛键生成逻辑`                      | 拒绝 A3，原因指出 scope 为空括号                |
| T07  | 标题 82 字符                                      | 拒绝 A8，原因给出当前长度与上限 78              |
| T08  | 标题 + 正文，正文某行 140 字符                    | 拒绝 C4，原因给出该行长度与上限 118             |
| T09  | 正文含 6 条要点                                   | 拒绝 C3                                         |
| T10  | 正文要点以 `* ` 开头                              | 拒绝 C2                                         |
| T11  | 标题与正文之间只有单个换行                        | 拒绝 C1                                         |
| T12  | 消息内含 `======` 分隔线                          | 拒绝 B2                                         |
| T13  | 消息内含两条标题行                                | 拒绝 B1，原因须点出第二条标题内容               |
| T14  | `feat(api)!: 移除兼容` 无 `BREAKING CHANGE` 脚注  | 拒绝 D3                                         |
| T15  | `revert: 新增 --staged 参数` 无 `Refs:`           | 拒绝 D4                                         |
| T16  | 输出以 ``` 围栏包裹                               | 拒绝 E1                                         |
| T17  | 空 diff                                           | 输出 `chore: 无实质变更`，通过全部校验          |
| T18  | 二进制文件变更                                    | 通过，且消息不含二进制内容描述                  |
| T19  | 连续 3 次输出 `feature(cli): ...`                 | 第 3 次后中止，未执行提交，原样展示最后一次结果 |
| T20  | 一次命中 A4 与 C4                                 | 失败原因同时列出两条，合并为一次重试            |

## 非目标

- 不校验代码本身的正确性，也不替代文件审查门禁
- 不做 semver 版本推算，版本号推断交由后续发布流程
- 不对原有提交历史做改写或批量修正（仅对新生成的消息生效）
- 规则清单暂不可由用户按需增删；需要自定义 type 或行宽时另行开需求

## 开放问题

1. 允许用户手工改写后绕过 L1 校验吗？倾向：不允许绕过，但允许改写后重新校验通过再提交。
2. 是否提供 `--no-verify-message` 之类的应急开关？倾向：不提供，避免开关成为常态。
3. L2 判定（语言类）命中时是告警放行还是计入重试？倾向：告警放行，但落日志。
4. 78 / 118 字符上限与「要点不超过 5 条」是否允许用户按项目配置？倾向：先固定并保持单一来源，自定义能力另行开需求。
