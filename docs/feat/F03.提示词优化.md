# 提示词优化

## 概述

当前项目的提示词（位于 `src/domain/commit-message/prompts.ts` 和 `src/domain/file-review/prompts.ts`）采用**一段式自然语言**风格，所有指令集中在一个或几个段落中，结构松散，边界模糊。优化目标是参考 WorkBuddy 系统提示词的写作风格，将其重构为**结构化、指令化、分节化**的提示词框架。

## 核心变更

| 维度 | 当前风格 | 优化后风格 |
|------|---------|-----------|
| 结构 | 一段式自然语言段落 | XML 节标记分节 |
| 指令 | 隐含在描述中 | 明确的指令化段落 |
| 规则 | 内联在描述中 | 编号规则，结构化列出 |
| 行为约束 | 弱约束（"请"，"建议"） | 强约束（"必须"，"禁止"） |
| 示例 | 嵌入在段落中 | 独立的 `<examples>` 节 |
| 输出格式 | 自然语言要求 | 明确的格式约束 |

## XML 节标记结构规约

重构后的提示词统一采用以下基本骨架（各提示词按需选用子集）：

```xml
<role>
  角色定义。一句话描述这个 AI 扮演什么角色。
</role>

<context>
  执行上下文。说明当前场景、输入来源、输出用途。
</context>

<task>
  核心任务。指明 AI 需要完成的主要目标。
</task>

<rules>
  编号的规则列表。每条规则是独立的约束条件：
  1. 强制性格式要求
  2. 内容规范
  3. 命名约定
  4. 其他硬性约束
</rules>

<examples>
  示例展示。每条示例以编号列出，展示输入输出对应关系。
</examples>

<output>
  输出约束。包括格式、语言、禁止内容等。
</output>
```

## 影响范围

需要重写以下 4 个提示词常量：

| 文件 | 常量 | 用途 | 工作量评估 |
|------|------|------|-----------|
| `src/domain/commit-message/prompts.ts` | `SYSTEM_PROMPT` | 通用提交信息生成 | 大（内容最复杂，需完整重构） |
| `src/domain/commit-message/prompts.ts` | `PARTIAL_SYSTEM_PROMPT` | 分批提交局部草稿 | 中（在通用版基础上裁减） |
| `src/domain/commit-message/prompts.ts` | `MERGE_SYSTEM_PROMPT` | 分批草稿合并 | 小（逻辑简单） |
| `src/domain/file-review/prompts.ts` | `REVIEW_SYSTEM_PROMPT` | 文件审查 | 中（需 JSON 输出约束） |

## 验收标准

1. **结构正确**：每个提示词使用 XML 节标记分节，标记名语义明确
2. **指令清晰**：每条要求以明确的指令形式（"必须"、"禁止"、"应当"）表述，不使用模糊祈使句
3. **行为约束**：已知的边界情况（如空 diff、二进制文件、超大变更）有明确的处理规则
4. **输出稳定**：同一 diff 多次调用生成的提交信息在语义上一致
5. **兼容性**：优化后的提示词不改变 `generator.ts`、`batch.ts`、`reviewer.ts` 中的调用逻辑和预期返回格式
6. **回归测试**：用项目历史 diff 测试，输出格式符合 Conventional Commits 规范，类型选择合理

## 注意事项

- 分批场景下（`PARTIAL_SYSTEM_PROMPT`），需要通过 `<context>` 节明确告知 LLM 这是部分 diff，避免对不完整的上下文做出错误判断
- 合并场景下（`MERGE_SYSTEM_PROMPT`），需要通过 `<rules>` 节明确去重和冲突处理规则（如不同草稿对同一文件的描述不一致时的取舍策略）
- 文件审查场景下（`REVIEW_SYSTEM_PROMPT`），`<output>` 节需使用 JSON Schema（而非自然语言描述）来约束返回格式
- 所有提示词要保持角色一致（"Git 提交信息专家"），避免不同 prompt 之间角色定义冲突
- 注意 token 预算：结构化标记会增加提示词长度，需确保分批阈值（`MAX_BATCH_INPUT_TOKENS`）留有足够余量
