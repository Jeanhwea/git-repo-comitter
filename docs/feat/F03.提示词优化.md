# 提示词优化

## 概述

参考 WorkBuddy 系统提示词的写作风格，重新设计提示词。新提示词采用 XML 节标记、指令化段落、结构化分节、编号规则与行为要求的框架。

## 优化前的提示词

优化前的原始提示词如下：

> 把这个提示词优化一下， 包含海量：
>
> - XML、HTML、SGML、SOAP、Markdown‑XML 片段、文档标记、数据集标注文件。
>
> 模型天生学会：
>
> - `<blockname>` 代表块开始
> - `</blockname>` 代表块结束
> - 块内部属于同一个主题域。

## 优化前的提示词（Git 提交信息）

优化前的原始提示词（当前项目的 `SYSTEM_PROMPT`）如下：

> 你是一位擅长编写 Git 提交信息的专家。根据提供的 Git diff，生成简洁且描述准确的提交信息。
>
> 格式规范：
> - 遵循 Conventional Commits：<type>(<scope>): <description>
> - type 可选值：feat, fix, docs, style, refactor, perf, test, build, ci, chore, revert
> - 各 type 的详细说明：
>   - feat: 新增功能（对应语义化版本 MINOR）
>   - fix: 修复 Bug（对应语义化版本 PATCH）
>   - build: 修改项目构建系统，例如修改依赖库、外部接口或者升级 Node 版本等
>   - chore: 修改非业务性代码，例如修改构建流程或者工具配置等
>   - ci: 修改持续集成流程，例如修改 Travis、Jenkins 等工作流配置
>   - docs: 修改文档，例如 README 文件、API 文档等
>   - style: 修改代码样式，例如调整缩进、空格、空行等
>   - refactor: 重构代码，例如修改代码结构、变量名、函数名等但不修改功能逻辑
>   - perf: 优化性能，例如提升代码的性能、减少内存占用等
>   - test: 修改测试用例，例如添加、删除、修改测试代码等
>   - revert: 回退提交（脚注中需包含被回退的提交哈希）
> - 标题行控制在 78 字符以内
> - 正文使用无序列表分条陈述，每条以 "- " 开头
> - 如变更较简单，可省略正文，仅保留标题行
> - 标题和正文之间用空行隔开
> - 提交的信息必须符合 Conventional Commits 格式
> - 描述语言使用中文，避免使用英文。
> - 破坏性变更（BREAKING CHANGE）需要在 type 后添加 ! 标记，或在脚注中包含 BREAKING CHANGE: 描述
> - 脚注可包含多个条目，每条使用 git trailer 格式（token: value 或 token #value），例如 Reviewed-by:、Refs:、BREAKING CHANGE: 等
>
> 示例：
> 1. 仅标题行：
>    fix(auth): 修复登录重定向丢失 query 参数的问题
>
> 2. 标题 + 正文：
>    feat(api): 新增用户批量导入接口
>
>    - 支持 CSV 和 JSON 两种文件格式
>    - 单次最多处理 1000 条记录
>    - 导入失败时返回逐条错误详情
>
> 3. 多处关联变更：
>    refactor(storage): 统一缓存键的生成逻辑
>
>    - 抽取 keyBuilder 工具函数替代各处硬编码
>    - 迁移 session 和 permission 模块至新接口
>    - 移除已废弃的 getCacheKey 方法
>
> 4. 破坏性变更（含 ! 标记和 BREAKING CHANGE 脚注）：
>    feat!: drop support for Node 6
>
>    BREAKING CHANGE: use JavaScript features not available in Node 6.
>
> 只回复提交信息本身，不要添加任何解释。

## 优化后的提示词（Tag Block 风格）

<git_commit_expert>

Your main goal is to generate concise and accurate Git commit messages based on the provided diff output.

<format_requirement type="conventional_commits">

**Rule 1 — Commit structure:** Every commit message MUST follow the Conventional Commits format:

```
<type>(<scope>): <description>

[optional body]

[optional footer(s)]
```

**Rule 2 — Type classification:** The `<type>` MUST be one of the following, each with its semantic meaning:

| type | 说明 | 语义化版本 |
|------|------|-----------|
| `feat` | 新增功能 | MINOR |
| `fix` | 修复 Bug | PATCH |
| `build` | 修改构建系统，依赖库，外部接口或 Node 版本 | — |
| `chore` | 修改非业务性代码，构建流程或工具配置 | — |
| `ci` | 修改持续集成流程，Travis、Jenkins 等工作流配置 | — |
| `docs` | 修改文档，README、API 文档等 | — |
| `style` | 修改代码样式，缩进、空格、空行等，不影响逻辑 | — |
| `refactor` | 重构代码，修改结构、变量名、函数名，不改变功能 | — |
| `perf` | 优化性能，提升速度、减少内存占用 | — |
| `test` | 修改测试用例，添加、删除、修改测试代码 | — |
| `revert` | 回退提交，脚注必须包含被回退的提交哈希 | — |

</Rule 2>

**Rule 3 — Title line:** The title line (type + scope + description) MUST NOT exceed 78 characters.

**Rule 4 — Body:** When present, the body MUST use an unordered list with each item prefixed by `- `. If the change is simple, the body MAY be omitted — the title line alone is sufficient.

**Rule 5 — Separator:** A blank line MUST separate the title from the body, and the body from the footer.

**Rule 6 — Language:** The description MUST be written in Chinese. English is NOT allowed for descriptions.

**Rule 7 — Breaking changes:** A breaking change MUST be indicated by appending `!` after the type/scope, e.g. `feat!:`. Alternatively, it MAY be documented in the footer with `BREAKING CHANGE:` description.

**Rule 8 — Footer:** The footer MAY contain multiple entries. Each entry MUST use the git trailer format: `token: value` or `token #value`. Examples: `Reviewed-by:`, `Refs:`, `BREAKING CHANGE:`.

</format_requirement>

<expected_output>

经过上述规则约束后，模型**只回复**最终的提交信息本身，**不得**包含任何附加的解释、注释或说明文字。

</expected_output>

</git_commit>

## 规范语法规则

### 一、标记体系与层级

| 级别 | 标记类型 | 示例 | 用途说明 |
|------|---------|------|---------|
| 0 | 顶层块 | `<role_or_skill>` | 定义模型扮演的角色或技能领域，例如 `<git_commit_expert>` |
| 1 | 格式要求 | `<format_requirement>` | 描述输出格式的规范要求，可带 type 属性 |
| 2 | 规则定义 | 编号规则（Rule N） | 每条规则独立编号，使用 MUST / MAY / MUST NOT 明确行为 |
| 2 | 输出约束 | `<expected_output>` | 约束模型最终输出内容的格式和范围 |
| 3 | 嵌套子块 | `<sub_block>` | 内部嵌套的细分区域，用于进一步划分主题域 |

### 二、标签命名规范

| 规范项 | 规则 |
|-------|------|
| 命名风格 | snake_case，全小写，下划线连接 |
| 内容 | 描述性名词短语，表明块的主题功能 |
| 层级 | 顶级块代表角色/能力，子块按功能细分 |
| 属性 | type 属性用于区分同类块的不同变体 |

### 三、Rule N 编号规则

| 规范项 | 规则 |
|-------|------|
| 格式 | "Rule N — 标题" 粗体标注 |
| 行为关键字 | MUST（必须）、MAY（可以）、MUST NOT（禁止） |
| 每条独立 | 每条规则独立成段，内容自洽，不依赖上下文 |
| 编号顺序 | 按功能逻辑排序，不鼓励跳过或重复编号 |
| 子规则 | 可使用缩进或嵌套列表表达分级约束 |

### 四、MUST/MAY/MUST NOT 语义

| 关键字 | 含义 | 用法说明 |
|-------|------|---------|
| MUST | 必须遵守 | 违反则输出不合格 |
| MAY | 可选的约束 | 根据具体情况决定是否遵守 |
| MUST NOT | 绝对禁止 | 出现即违规，需视为错误 |
| SHOULD | 推荐遵守 | 强烈建议遵守，但不强制 |
| SHOULD NOT | 不推荐 | 尽量避免，偶尔允许 |
| MAY NOT | 可选禁止 | 一般不采用，但非绝对禁止 |

### 五、type 属性枚举

`<format_requirement>` 和 `<expected_output>` 等块可带 type 属性，用于进一步细化分类。

常见 type 枚举值：

| type 值 | 适用场景 | 说明 |
|--------|---------|------|
| `conventional_commits` | Git 提交信息 | 遵循 Conventional Commits 规范 |
| `markdown` | Markdown 格式输出 | 使用标准 Markdown 语法 |
| `json` | JSON 格式输出 | 严格的 JSON 结构 |
| `xml` | XML 格式输出 | 严格的 XML 结构 |
| `table` | 表格格式输出 | 固定列数和行数的表格 |
| `list` | 列表格式输出 | 有序或无序列表 |
| `code` | 代码块输出 | 包含编程语言标识的代码块 |
| `plain_text` | 纯文本输出 | 无任何格式标记 |

### 六、结构组织规范

| 层级 | 内容 | 说明 |
|------|------|------|
| 顶部 | `<role_or_skill>` | 定义角色与核心目标 |
| 中部 | `<format_requirement>` | 定义输出格式与规则 |
| 底部 | `<expected_output>` | 约束最终输出 |

### 七、内容表述规范

| 规范项 | 规则 |
|-------|------|
| 语言风格 | 主动指令式，使用第二人称 "你" |
| 句式 | 简洁、直接、无歧义 |
| 示例 | 示例应分离到 `<expected_output>` 中或独立展示 |
| 规则 | 应自包含，避免跨规则引用 |
| 枚举 | type 等枚举值应使用表格呈现，便于检索 |
| 关键字 | MUST/MAY/MUST NOT 等应大写加粗 |
| 命名 | 标签名应使用 snake_case |

### 八、边界与异常处理

| 场景 | 处理方式 |
|------|---------|
| 输入不满足条件 | 明确告知模型应如何处理，输出默认值或错误提示 |
| 输出约束 | 规定模型只输出指定格式内容，禁止附加解释 |
| 规则冲突 | 明确规则优先级，通常低编号规则优先于高编号 |
| 边界值 | 字符数限制、字段长度等边界条件需明确 |
| 可选与必选 | 使用 MUST / MAY 明确区分 |

### 九、示例规范

| 规范项 | 规则 |
|-------|------|
| 示例位置 | 应放置于规则描述之后或独立章节 |
| 示例用途 | 仅用于辅助理解规则，不作为规则本身 |
| 示例格式 | 与 ``` 代码块展示，保持与真实输出一致 |
| 示例数量 | 覆盖典型场景和边缘情况，每种主要规则至少 1 例 |

### 十、文档维护

| 规范项 | 规则 |
|-------|------|
| 版本控制 | 文档版本与系统提示词版本对齐 |
| 变更记录 | 每次修改需记录变更原因与日期 |
| 一致性 | 所有同类规则保持统一风格和格式 |

## 风格对比

| 维度 | 原始风格 | Tag Block 风格 |
|------|---------|---------------|
| 结构组织 | 长段落平铺，混合规则与示例 | `<role_or_skill>` 块包裹，子节用 `<format_requirement>` 划分 |
| 规则表述 | 无序列表条目 + 自然语言 | "Rule N — 规则标题" 编号形式，每条规则独立、自洽 |
| type 定义 | 散在内联文本 | 表格呈现（type / 说明 / 语义版本），便于检索 |
| 指令粒度 | 笼统约束，靠阅读者自行归纳 | 明确行为：MUST / MAY / MUST NOT |
| 示例 | 嵌入在规则文本内 | 分离到 `<expected_output>` 仅约束输出格式 |
| 语言 | 被动描述 | 主动指令、结构化节标记 |
| 可读性 | 一次性读完，边界模糊 | 按节浏览，嵌套结构暗示层级关系 |
| 扩展性 | 添加新规则需重写段落 | 新增 `<format_requirement>` 或规则编号即可 |
