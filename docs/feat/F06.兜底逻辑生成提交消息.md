# 兜底逻辑生成提交消息

## 背景

`grc` 的核心能力是调用大语言模型生成 Conventional Commits 格式的提交信息。这意味着大模型是整个流程的必需组件：`config.llm.model` 与 `config.apiKey` 共同决定了能否成功调用 LLM。

当前 `executeCommit` 在执行流程的第一步（`commit-flow.ts:165`）就校验 `config.apiKey`。如果 apiKey 缺失，直接抛出 `CONFIG_MISSING` 错误并终止流程，不给用户任何变通使用的机会。

## 现状

| 环节 | 当前行为 |
|------|----------|
| `config.apiKey` 为空 | 抛出 `CONFIG_MISSING`，流程中止 |
| `config.llm.model` 为空 | 未单独校验，默认值 `deepseek-v4-flash` 补齐，实际调用 LLM 时才失败 |
| diff 为空 | 提示词中约束输出 `chore: 无实质变更`（F04 F1） |
| LLM 调用失败 | 抛出 `LLM_FAILED`，流程中止 |
| LLM 返回空内容 | 抛出 `LLM_FAILED`，流程中止 |

当前没有任何机制允许用户在未配置大模型的情况下完成 git 提交。

## 差距

1. **无 LLM 则全流程不可用**：apiKey 缺失直接阻断，不考虑「不用 LLM 也能提交」的兜底路径。
2. **判断粒度不够细**：代码将「配置缺失」与「LLM 不可用」捆绑处理——缺少 apiKey 不等于用户不想要提交，也许用户愿意接受规则生成的提交消息。
3. **规则生成可行性未利用**：F04 的 F1 场景（空 diff → `chore: 无实质变更`）本身就是一种兜底；非空 diff 也可以通过分析文件变更类型生成基础提交消息，虽然不如 LLM 生成的精细，但足以满足「先提交再说」的需求。

## 路径

### 方案：基于 diff 统计的规则生成

在 `domain/commit-flow.ts` 中，将「调用 LLM 生成提交消息」改为**可降级**的两阶段路径：

```
 diff 非空且 LLM 可用 → LLM 生成（现有流程）
 diff 非空且 LLM 不可用 → 规则生成（新增兜底）
 diff 为空 → chore: 无实质变更（现有逻辑下沉）
```

#### 判定条件

LLM 不可用的判定：`!config.llm.model && !config.llm.temperature` 同时未设置（即未指定任何 LLM 相关参数，使用纯默认值也视为未配置）。

更精确地说，以下任一条件满足即为「LLM 可用」：

1. `config.apiKey` 非空，且 `config.llm.model` 非默认值（即用户显式配置了模型）
2. `config.apiKey` 非空，用户接受使用默认模型

以下条件即为「LLM 不可用」：

1. `config.apiKey` 为空或空字符串，且用户未在 init 交互中配置——此时进入兜底路径。
2. 不需要新增一个单独的开关或 CLI 参数，缺失 apiKey 本身就是用户尚未完成 LLM 配置的信号。

#### 规则生成逻辑

基于 `infra/git/changes.ts` 获取的 `ChangeSet`（已在 `executeCommit` 流程中前置获取）生成提交消息：

```
输入: ChangeSet（files / newFiles / binaryFiles）

步骤:
1. 收集所有文件变更类型（add/modify/delete/rename）
2. 推断 type:
   - 存在新增文件 → "feat"
   - 存在删除文件 → "feat"（新增优先），若无新增则 "refactor"
   - 仅修改既有文件 → "fix"（若无语义信息则 "chore"）
   - 仅二进制文件变更 → "chore"
   - 全新文件+二进制 → "feat"
3. 聚合 scope:
   - 取文件路径的共同顶层目录（最长公共前缀的第一个路径段）
   - 若文件分散在超过 3 个顶层目录，不设 scope
4. 生成 description:
   - 根据 type 和文件数量生成标准描述
   - "feat": "新增 {文件名} 等 {N} 个功能文件"
   - "fix": "修复 {文件名} 等 {N} 个文件的问题"
   - "refactor": "重构 {文件名} 等 {N} 个文件"
   - "chore": "更新 {N} 个文件"
5. 生成 body:
   - 列出变更的每类文件（新增/修改/删除），每类一行要点
   - 每个要点格式：`- {动作} {文件数} 个文件：{文件名列表（最多列出 5 个，超长用等代替）}`
6. 输出格式必须满足 F04 的校验规则，确保 `validateCommitMessage` 能通过
```

#### 提示词约束

当 LLM 可用时，在 `prompts` 中补充一条兜底约束，确保 LLM 生成的消息在 apiKey 失效等边缘场景下仍然有其价值（非本次范围）。

#### 关键变更文件

| 文件 | 变更内容 |
|------|----------|
| `src/domain/commit-flow.ts` | 在调用生成提交消息前增加 LLM 可用性判定，不可用时走规则生成 |
| `src/domain/commit-message/fallback.ts` | **新增**：规则生成提交消息的逻辑（拆分自 `commit-flow.ts`） |
| `src/domain/commit-flow.ts` | 下沉 F04 F1 场景（空 diff → chore: 无实质变更）至 flow 层，不依赖 LLM |
| `src/shared/errors.ts` | 无需新增错误码，现有 `NO_CHANGES` 覆盖空 diff 场景 |
| `src/lib.ts` | 若需要对外暴露规则生成能力，在公共 API 中导出 `generateFallbackMessage` |

#### 不影响的部分

- `infra/llm/` —— 无变更，兜底路径不调用 LLM
- `prompts/` —— 无变更，兜底路径不依赖提示词
- `shared/` —— 无变更
- `app/` —— CLI 的选项、渲染、退出码均无需变更
- `docs/feat/F04` —— 已有校验规则同样适用于规则生成结果，无需修改

## 开放问题

1. **scope 推断的颗粒度**：依据文件路径的公共顶层目录作为 scope，对于跨多层目录的变更是否足够精确？例如 `src/a/b/c.ts` 和 `src/a/d/e.ts`，顶层公共目录是 `src`，scope 为 `src` 过于宽泛。是否应使用公共前缀的倒数第一或第二个路径段？

2. **description 的语言风格**：规则生成的描述由于缺乏语义理解，只能基于文件名和变更类型生成模板化句子，与 LLM 生成的语义化描述有差距。是否需要在 description 中显式标明「规则生成」字样（如 `chore(fallback): 规则生成提交消息`），以便用户识别这是兜底结果？

3. **用户知情权**：当触发兜底路径时，是否应该通过 `emitProgress` 告知用户「大模型未配置，使用规则生成提交消息」？倾向：告知，避免用户困惑为何提交消息质量下降。

4. **二进制文件的变更描述**：当前 `ChangeSet` 中 `binaryFiles` 只记录文件名，不知具体变更内容——这对于规则生成而言足够，但对用户来说信息量有限。是否接受仅记录二进制文件名的描述？倾向：接受，对齐 F04 F2。

5. **body 的最大文件列表长度**：规则生成中要点列出的文件名上限设为 5 是否合适？过多则 body 过长，过少则信息不足。

6. **是否允许用户在 `~/.grc/config.json` 中配置最小规则描述**：比如指定一个固定的 description 前缀，用于替代自动推断的描述。当前倾向：不开放，仅在 LLM 未配置时触发，规则描述同一份。
