# 兜底逻辑生成提交消息

## 背景

`grc` 的核心价值是利用大模型（LLM）将 git 暂存区 diff 转化为符合 Conventional Commits 规范的中文提交消息。但这个价值有一个前提：用户必须正确配置了 LLM（apiKey、endpoint、model）。

在以下两种场景下这个前提不成立：

1. **用户未配置 LLM**（apiKey 为空，或在极简模式下使用 `grc` 不想配置 LLM）——此时不应强求用户配置，而应提供一个可工作的退路。
2. **LLM 调用连续失败**——LLM 服务不可用、API 返回异常、或即便重试 3 次后校验仍不通过——此时应当降级为一个规则化方案，而非直接中止整个提交流程。

两种场景的共性是：**不能用 LLM，但仍然要为变更生成一条合规的提交消息**。差别在于：场景 1 可以提前预判，直接在 `executeCommit` 入口处跳转；场景 2 是在 LLM 调用链路已走完、重试已耗尽之后才触发。

## 现状

### 兜底模块已存在

`src/domain/commit-message/fallback.ts` 实现了 `generateFallbackMessage` 函数，它接收 `ChangeSet` 对象，通过规则化方式生成提交消息：

- **type 推断**：通过文件变更特征（新增/修改/删除、文件扩展名、目录结构）推断 `feat`/`fix`/`docs`/`build`/`chore`/`refactor` 等类型，按优先级裁决。
- **scope 推断**：从文件路径的一级目录提取作为 scope 候选。
- **description 构建**：根据 type 和文件数量生成描述文本，多个 type 时附加标记。
- **body 要点生成**：按文件操作类型（新增/修改/删除）分组，以要点形式列出文件路径。
- **行宽约束**：标题不超过 78 字符、要点不超过 10 条，与 `shared/commit-limits` 一致。
- **空变更处理**：直接返回 `chore: 无实质变更`。

### 兜底模块尚未接入提交流程

在 `src/domain/commit-flow.ts` 的 `executeCommit` 中：

- 第 165~170 行：apiKey 为空时直接抛 `CONFIG_MISSING`，没有尝试兜底。
- 第 210~213 行：LLM 生成失败时抛 `VALIDATION_FAILED` / `LLM_FAILED`，没有捕获降级。

兜底模块虽已实现，但未被任何调用路径触发，处于「有代码无入口」的状态。

## 差距

| # | 差距 | 影响 |
|---|------|------|
| G1 | `apiKey` 为空时抛异常退出，未提供规则化替代方案 | 用户未配 LLM 就无法使用 `grc` 的基本功能，降低了工具的适应场景 |
| G2 | LLM 连续失败后直接中止，未降级 | 临时网络故障或服务波动会导致提交中断，用户不满意 |
| G3 | 兜底生成需要 `ChangeSet`（结构化变更集），而当前流程持有的是纯文本 diff | 调用 `generateFallbackMessage` 前需要获取 `getStagedChangeSet` 的数据 |
| G4 | 兜底消息是否仍要走 `validateCommitMessage` 校验？当前 `generateFallbackMessage` 内部未调用校验 | 若兜底生成有不符合规则的边界情况，直接写入提交历史可能造成污染 |
| G5 | 用户对降级事件无感知 | 兜底后应在输出中明确提示用户当前是降级模式，而非假装一切正常 |

## 路径

### P1. `apiKey` 为空时走兜底——时机：`executeCommit` 入口处

在第 165~170 行，不抛异常，改为：

```ts
if (!config.apiKey) {
  emitProgress("未配置 LLM，使用规则化模式生成提交信息...\n");
  const { message } = await measure("生成提交信息（兜底）", async () => {
    const changeSet = getStagedChangeSet(repoPath);
    return generateFallbackMessage(changeSet);
  });
  await measure("执行 git commit", () => gitCommit(message, repoPath));
  // ... 返回 CommitSuccess
}
```

前置条件：需要导入 `getStagedChangeSet` 和 `generateFallbackMessage`。

### P2. LLM 调用失败后走兜底——时机：`generateCommitMessageBatched` 异常抛出点

在 `commit-flow.ts` 第 211~213 行，捕获 `VALIDATION_FAILED` / `LLM_FAILED` 两种错误，降级到 `generateFallbackMessage`：

```ts
let message: string;
let batchCount = 1;
let isFallback = false;
try {
  const result = await generateCommitMessageBatched(diff, config);
  message = result.message;
  batchCount = result.batchCount;
} catch (err) {
  if (err instanceof GrcError && (
    err.code === "VALIDATION_FAILED" || err.code === "LLM_FAILED"
  )) {
    emitProgress("LLM 生成失败，降级为规则化模式...\n");
    const changeSet = getStagedChangeSet(repoPath);
    message = generateFallbackMessage(changeSet);
    isFallback = true;
  } else {
    throw err;
  }
}
```

P2 的实现复杂度高于 P1：需要区分 LLM 失败的类型，并只在重试 3 次仍然失败后才触发（`infra/llm/retry.ts` 已经封装了重试逻辑，只需在最终错误上做区分即可）。

### P3. 兜底消息通过 `validateCommitMessage` 校验

在 `generateFallbackMessage` 函数末尾（第 269 行之后），增加校验调用：

```ts
import { validateCommitMessage } from "./checker";
// ...
const validation = validateCommitMessage(message);
if (!validation.valid) {
  log.warn(`fallback 生成的消息未通过校验，已修正`, validation.failures);
  // 取最后一次生成结果，记录告警但不阻断（兜底模式不应再重试）
}
```

考虑到兜底模式本身已经是降级，校验失败不应再触发重试循环——只需在日志中记录告警，避免输出未通过校验的消息进入提交历史。如果校验失败则做一次最终修正（例如对标题长度做硬截断）。

### P4. 用户感知提示

兜底触发时应在 `emitProgress` 中明确告知用户当前处于降级模式，例如：

```
未配置 LLM，使用规则化模式生成提交信息...
  (已降级：提交消息由规则生成，不含 AI 语义分析)
```

### P5. 优先级

| 优先级 | 工作项 | 依赖 |
|--------|--------|------|
| P1 | apiKey 为空时走兜底 | 无 |
| P2 | LLM 失败后走兜底 | 无 |
| P3 | 兜底消息过校验 | P1、P2 完成后 |
| P4 | 用户感知提示 | 随 P1、P2 一并实现 |
| P5 | 补充测试用例 | P1~P2 完成后 |

## 开放问题

1. **P2 场景下「重试 3 次仍失败」的判定点**：`infra/llm/retry.ts` 的 `callWithValidation` 目前对重试耗尽后抛出的 `GrcError` 是否区分了 `VALIDATION_FAILED` 和 `LLM_FAILED`？需要确认错误码体系是否足够区分，以便在 `commit-flow.ts` 层面精确捕获。若不区分，是否要在 retry 层增加一个新的 `RETRY_EXHAUSTED` 码？

2. **兜底消息的语义质量**：规则化生成的消息缺乏语义理解，例如无法区分「重构是为了后续特性做准备」还是「修复 bug」的上下文。降级提示中是否应建议用户手动编辑？倾向：降级 + 提示用户可通过 `git commit --amend` 自行修正。

3. **是否允许用户关闭兜底**：若用户明确要求「LLM 失败即中止，不要降级」，是否提供配置项？倾向：不提供，兜底是一个安全网而非默认行为，关闭安全网无实际收益。

4. **P1 与 P2 的代码复用**：两个入口都会调用 `getStagedChangeSet` + `generateFallbackMessage` + `gitCommit`，建议抽象为一个 `tryFallback` 辅助函数，避免重复代码。

## 结论

兜底逻辑的核心价值在于：**当 LLM 不可用时（无论是因为未配置还是调用失败），`grc` 仍然能完成一次基本的 `git commit`**。这降低了工具的使用门槛，也提高了对临时故障的容忍度。

当前 `fallback.ts` 中规则化生成的能力已经满足需求，接下去的工作是将其正确接入提交流程，并在两种触发场景下都能给出明确的用户反馈。P1（apiKey 缺失）和 P2（LLM 失败）是两个独立的触发条件，可以同步实现，但 P1 的改动更轻、风险更低，建议优先落地。
