# F09. 支持跳过 Git 提交的 Hook

原始需求（一句话）：提交时加一个选项，让 GRC 能像 `git commit --no-verify` 一样跳过 Git Hook。

> 本文按「背景 → 现状 → 差距 → 路径 → 开放问题 → 结论」组织；现状、差距同时记录实现前状态与本次收敛结果。

## 背景

仓库常在 `pre-commit` / `commit-msg` 等 Hook 里跑 lint、测试或提交信息校验。Hook 脚本报错时，Git 会直接拦截提交。但很多场景只是想临时提交一次（本地存档、WIP、切换分支），此时去修 Hook 或临时改脚本成本偏高，也容易污染工作区。

`git commit` 原生提供 `--no-verify` 参数绕过这些 Hook，用户希望 GRC 也有同等的「一键跳过」能力。

## 现状

**Git 原生能力**：`git commit --no-verify -m "..."` 跳过 pre-commit 与 commit-msg 等 Hook，仅作用于本次提交。

**实现前（GRC）**：

- CLI 全局选项只有 `-s/--staged-only`、`-V/--verbose`、`--debug`、`--trace`，没有跳过 Hook 的入口；
- `infra/git/repo.ts` 的 `gitCommit(message, cwd)` 固定拼 `["commit", "-m", message]`，没有追加参数的口子；
- 从 CLI 到 `executeCommit` 的请求对象里也没有承载该开关的字段。

**实现后（本次 F09，已落地）**：

- 新增 CLI 参数 `-n, --no-verify`，用法 `grc -n` / `grc --no-verify`；
- 开关沿 `program.ts → commands/commit.ts → domain/commit-flow.ts → infra/git/repo.ts` 透传，最终在 `git commit` 命令上追加 `--no-verify`；
- 库侧 `CommitRequest.noVerify` 与 `gitCommit(message, cwd?, noVerify?)` 同样可用，CLI 与库行为一致；
- 不带参数时命令与实现前完全一致，Hook 照常执行。

## 差距

| # | 实现前的差距 | 收敛结果 |
|---|---|---|
| 1 | CLI 无跳过 Hook 的参数，用户只能回命令行手写 `git commit --no-verify` | 已消除：新增 `-n, --no-verify` |
| 2 | `gitCommit` 参数写死，无法追加 `--no-verify` | 已消除：增加可选第三参数，缺省 `false` 保持兼容 |
| 3 | CLI → 领域层 → infra 的请求链路没有承载该开关 | 已消除：`CliOptions` → `CommitOptions` → `CommitRequest` 全链路透传 |
| 4 | 兜底（无 apiKey）与正常（LLM 生成）两条提交路径可能行为不一致 | 已消除：两处 `gitCommit` 调用都传入 `noVerify` |

仍刻意保留的边界（非缺陷，取舍见「开放问题」）：不做 Hook 失败后的自动重试、不做细粒度 Hook 选择、不把开关写进配置文件。

## 路径

### 用法

```bash
grc --no-verify   # 或 grc -n
grc -n -s         # 可与其他全局选项组合
```

### 改动落点

| 层 | 文件 | 改动 |
|---|---|---|
| CLI | `src/app/cli/program.ts` | 注册 `-n, --no-verify`；把 commander 的负向布尔 `verify` 反转为正向 `noVerify` |
| 应用 | `src/app/commands/commit.ts` | `CommitOptions` 增加 `noVerify` 并传给 `executeCommit` |
| 领域 | `src/domain/commit-flow.ts` | `CommitRequest` 增加 `noVerify`；兜底与正常两条提交路径都透传 |
| 基础设施 | `src/infra/git/repo.ts` | `gitCommit(message, cwd?, noVerify?)`，`noVerify` 时拼 `["commit", "--no-verify", "-m", message]` |

### 关键决策

1. **参数与 Git 同名**：CLI 直接叫 `--no-verify`，用户无需记两套名字；附短选项 `-n` 便于「一键」使用。
2. **负向选项只反转一次**：commander 会把 `--no-verify` 解析成 `verify`（未传 `true`、传入 `false`），与业务语义方向相反。仅在 `program.ts` 的 action 处做一次 `noVerify: options.verify === false`，下游统一用正向布尔，避免多处把方向看反。
3. **向后兼容**：`gitCommit` 保留原两参数签名，第三参数可选且缺省 `false`；既有调用方无需改动。
4. **显式、单次、不落配置**：开关必须每次显式输入，只影响本次提交，不写 `~/.grc/config.json`，避免长期绕过校验。

### 验收

- `pnpm check` / `pnpm lint` / `pnpm test`（27 个既有用例）/ Prettier / `pnpm build`（含浏览器入口护栏）全部通过。
- 端到端：临时 Git 仓库挂一个必定失败的 `pre-commit` hook —— 带 `noVerify` 时提交成功（提交数 1）；不带参数时提交被拦截并输出 `HOOK_BLOCKED`（提交数仍为 1）；`-n` 短选项与 `--no-verify` 行为一致。

## 开放问题

原四项已在实现时确认，结论如下：

1. **对应哪个 Git 参数** → 已确认 `--no-verify`，跳过 pre-commit / commit-msg 等 Hook。
2. **交互形态** → 已确认命令行 flag（含短选项），不做交互式勾选或快捷键。
3. **是否细粒度控制** → 本期不做；`--no-verify` 是 Git 提供的全量跳过，暂不区分具体 Hook。
4. **是否加风险提示** → 本期不加；开关需显式输入且仅单次生效，风险由用户自担。

留待后续评估（本期明确不做）：

- **失败后自动重试**：Hook 报错时自动询问「是否跳过 Hook 重提」？会让一次命令产生两次提交尝试，先保持显式。
- **配置默认值**：是否允许在 `~/.grc/config.json` 固化 `noVerify`？倾向不做，避免全局绕过校验。
- **CLI 错误可读性**：Hook 失败时目前透出底层 `git` 报错，未包装成带错误码的 `GrcError`；可与后续统一错误处理一并收敛。
- **公共 API 文档同步**：`README.md` 公共 API 表与 `S01` 仍写 `gitCommit(message, cwd?)`，未列第三参数，待补。

## 结论

F09 已实现并验收：GRC 新增 `-n, --no-verify`，一个参数即可在 `git commit` 时跳过 Git Hook，等价于原生 `git commit --no-verify`。

- **行为**：带参数跳过 Hook；不带参数与实现前完全一致，Hook 照常拦截。
- **性质**：显式、单次、不落配置、向后兼容；兜底与 LLM 两条提交路径行为一致。
- **边界**：不做自动重试、不做细粒度 Hook 选择、不提供全局默认，相关取舍已记入「开放问题」。
