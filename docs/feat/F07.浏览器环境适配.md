# 浏览器环境适配

## 背景

F05 把 grc 抽象为库后，真实的嵌入场景有两个，且都不在 Node 进程里：

1. **Tauri 桌面应用的 WebView**（WebView2 / WKWebView / WebKitGTK）——应用想内联「生成提交信息 → 回填输入框让人改」，而不是 `spawn` 一个 CLI 子进程；
2. **Next.js 全栈项目的浏览器端**——client component 里直接调用生成能力，API Key 走 BYOK（用户自带钥匙），不经过服务端。

但当前产物（`git-repo-comitter@1.3.0`）在这两个环境都跑不起来，实测证据：

- `dist/index.js` 顶层直接 `import ... from "fs" / "os" / "path" / "child_process"`，Vite 打进浏览器必然解析失败；
- OpenAI SDK 的浏览器判定是 `typeof window !== "undefined" && window.document && navigator`，Tauri WebView 三条全中，构造客户端时未传 `dangerouslyAllowBrowser` 即拒绝启动（全包搜索该标志 0 次命中，`AppConfig` 也只有 `llm` / `apiKey` / `endpoint` 三个字段，没有留口子）；
- `shared/logger.ts:30` 在模块顶层求值 `process.env.GRC_LOG_LEVEL`，浏览器里 `process` 全局不存在，**import 瞬间就抛 ReferenceError**，比模块解析失败炸得更早。

核心诉求：**同一套代码，Node CLI 与浏览器端都能用；浏览器端至少获得完整的「生成 + 校验」链路**。

## 现状

### Node 内置依赖盘点（`src/` 实测）

| 依赖 | 位置 | 被谁触发 |
|---|---|---|
| `child_process` | `infra/git/runner.ts:8`（`execFileSync`，封装为 `execGit`） | `getStagedDiff` / `gitCommit` / `gitAddAll` / `isGitRepo` / `executeCommit` 全链路 |
| `fs` / `os` / `path` | `config/loader.ts:15-17` | `loadUserConfigFile` / `saveUserConfig`（读写 `~/.grc/config.json`） |
| `process.env`（顶层求值） | `shared/logger.ts:30` | 任何 import 库的代码路径 |
| `openai` SDK 浏览器拦截 | `infra/llm/transport/client.ts:26`（`new OpenAI({ apiKey, baseURL })`） | 所有 LLM 调用 |
| `readline/promises` | `app/cli/input.ts` | 仅 CLI 交互，**不在** `lib.ts` 入口图内 |

`vite.config.ts:31-38` 的 `external` 列表（`fs` / `path` / `os` / `child_process` / `readline/promises`）等于官方声明：这些模块永远不会进产物，运行时由宿主提供。

### 纯核已就绪

以下模块零环境依赖（或仅类型依赖，打包时擦除），是浏览器端可直接复用的资产：

| 模块 | 说明 |
|---|---|
| `prompts/**` | 提示词块与消息组装，纯文本函数 |
| `domain/commit-message/checker.ts` | Conventional Commits 校验（F04 规则） |
| `domain/commit-message/generator.ts` / `batch.ts` | 单批与分批生成流水线 |
| `domain/commit-message/fallback.ts` | 规则化兜底（F06） |
| `infra/llm/retry.ts` / `budget.ts` | 重试循环、token 预算 |
| `shared/{tokens,validation,errors,progress,time}.ts` | 估算、校验结论、错误、进度、计时 |
| `config/loader.ts` 的 `resolveConfig`（`:134`） | 纯函数配置解析，不读写文件 |

也就是说，浏览器端真正需要的 `generateCommitMessage` / `generateCommitMessageBatched` / `validateCommitMessage` 这条链路，本质是干净的；污染的只有 4 个接入点。

## 差距

| # | 差距 | 影响 |
|---|------|------|
| G1 | `lib.ts` 入口图传递依赖 4 个 Node 内置模块 | 浏览器打包在解析期即失败，无法 import |
| G2 | `logger.ts:30` 顶层读取 `process.env` | 浏览器 import 期 ReferenceError |
| G3 | openai 客户端构造缺浏览器放行 | LLM 调用被 SDK 主动拒绝 |
| G4 | 无浏览器产物与 `exports` 映射 | 即便打包成功，包描述也没有浏览器入口 |
| G5 | git 执行硬编码 `child_process`，无注入点 | 浏览器 / WebView 中无法替换执行机制；且 `execGit` 是同步签名，与 Tauri 的异步 IPC 天然不匹配 |

## 目标场景与数据流

两条链路的共同形态：**diff 在 Native 侧（Rust / Node）算好，以字符串传入浏览器；浏览器只负责生成与回填**。

```
Tauri 场景：

  Rust 侧                     WebView                          LLM API
  ┌────────────────┐  diff    ┌──────────────────────┐  fetch  ┌──────────┐
  │ tauri-plugin-  │ 字符串   │ import ... from      │ ◄──────► │ OpenAI   │
  │ shell 跑 git   │ ───────► │ "git-repo-comitter/  │  key 在  │ 兼容端点 │
  │ diff --cached  │  IPC     │ browser"             │  本地    │          │
  └────────────────┘          │ generateCommitMessage│          └──────────┘
                              │ → 回填输入框         │
                              └──────────────────────┘

Next.js 场景：

  Next server                  Client 组件                      LLM API
  ┌────────────────┐  server   ┌──────────────────────┐  fetch  ┌──────────┐
  │ route handler  │  action   │ "use client"         │ ◄──────► │ BYOK     │
  │ / action       │ ────────► │ import ... from      │  浏览器  │ 端点     │
  │ Node 版入口取  │  传 diff  │ "git-repo-comitter/  │  直连    │          │
  │ getStagedDiff  │           │ browser" 生成并回填  │          │          │
  └────────────────┘          └──────────────────────┘          └──────────┘
```

Next.js 场景中服务端用的是 `.`（Node）入口——仓库在服务器本地时最顺；生成步骤在客户端，key 不落服务器。若后续要藏 key，把生成那一步挪进 route handler 即可，纯核代码一份不动。

## 路径

### 核心思路：纯核 + 端口 + 双入口

```
        ┌─────────────┐  ┌──────────────┐  ┌──────────────────┐
        │  grc CLI    │  │ Tauri WebView│  │ Next.js client   │    消费方
        └──────┬──────┘  └──────┬───────┘  └────────┬─────────┘
               │                │                   │
        ┌──────▼──────┐  ┌──────▼───────────────────▼──────┐
        │  lib.ts     │  │  lib-browser.ts                 │    双入口
        │ Node 完整API│  │  仅纯函数侧 API                 │
        └──────┬──────┘  └──────┬──────────────────────────┘
               │                │
        ┌──────▼────────────────▼──────────────────────────┐
        │  纯核 core（两端共用，零环境依赖）                  │
        │  prompts · commit-message · config/resolve · shared│
        ├──────────────────────────────────────────────────┤
        │  端口 ports（接口 + 注册表，无实现）                │
        │  GitExecutor · ConfigStore · LlmTransport · getEnv│
        └──────┬───────────────────────────┬───────────────┘
               │ 默认装配                   │ 调用方注入
        ┌──────▼──────┐            ┌───────▼──────────────┐
        │ node/ 实现层 │            │ Tauri shell IPC 等   │
        │child_process│            │ 调用方自备实现        │
        │  fs · os    │            │                      │
        └─────────────┘            └──────────────────────┘
```

### 关键设计决策

| 编号 | 决策 | 理由 | 代价 |
|---|---|---|---|
| D1 | 用显式 `"./browser"` 子路径导出浏览器产物，不用 `"browser"` export condition 自动切换 | TypeScript 不解析 `"browser"` condition：打包器自动切产物时类型仍是 Node 版 d.ts，`getStagedDiff` 看着能调、一跑才炸，类型与运行时错位 | 浏览器消费者 import 路径多一段 `/browser` |
| D2 | openai SDK 单实现 + 浏览器探测补 `dangerouslyAllowBrowser`，不拆 transport | SDK v6 底层即 fetch，Node 18+ 同样走 fetch，一份代码两个环境 | 浏览器包多约两三百 KB；`chatCompletion` 已是单点，将来换 fetch 实现是局部手术 |
| D3 | `GitExecutor` 保持同步契约，不做 async 化；diff 由调用方（Rust / Node 侧）算好后传入 | Tauri IPC 是异步的，硬接需把 `execGit` 全链改 Promise，`getStagedDiff` 公开签名跟着破——那是动 F05 契约的 v2 工程 | 浏览器端不直接获得 git 读写能力（本方案也不需要） |
| D4 | `.` 入口公开 API 一个字节不改 | F05 契约、CLI 行为、现有 Node 调用方零感知 | 装配默认 executor 的逻辑放在入口文件内 |

### P1 —— 拆纯核（4 处，全机械改动，外部行为零变化）

1. **`shared/logger.ts:30`** —— `process.env.GRC_LOG_LEVEL` 加运行时守卫：

```ts
const currentLevel: LogLevel = normalizeLevel(
  typeof process !== "undefined" ? process.env?.GRC_LOG_LEVEL : undefined,
);
```

2. **`config/loader.ts` 拆分** —— 文件读写下沉到新建的 `config/user-file.ts`（`CONFIG_DIR` / `USER_CONFIG_PATH` / `loadUserConfigFile` / `saveUserConfig` + fs/os/path import 一并搬走）；`loader.ts` 只留 `DEFAULT_CONFIG` / `loadDefaultConfig` / `clampLlm` / `resolveConfig`（已确认为纯函数，`:134`）。
   受影响方：`app/config/load.ts:12,14` 与 `app/commands/init.ts:7,8` 改 import 路径；`lib.ts:21` 的再导出改指向 `@/config/user-file`，公开 API 不变。

3. **`infra/git/runner.ts` 端口化** —— 拆为两个文件：

```ts
// infra/git/executor.ts（零 node import）
export interface GitExecutor {
  exec(args: string[], options?: { cwd?: string; allowFailure?: boolean }): string;
}
let current: GitExecutor | null = null;
export function setGitExecutor(next: GitExecutor): void { current = next; }
export function execGit(args: string[], options = {}): string {
  if (!current) throw new GrcError("git 执行器未装配：Node 入口会自动装配，其他环境请 setGitExecutor", "GIT_FAILED");
  return current.exec(args, options);
}
```

现有 `execFileSync` 实现原样搬入 `node/git/child-process-executor.ts`；`changes.ts:1` / `diff/build.ts:1` / `repo.ts:9` 只改 import 路径。

4. **`infra/llm/transport/client.ts:26`** —— `createClient` 加浏览器探测：

```ts
const isBrowser = typeof window !== "undefined" && typeof document !== "undefined";
return new OpenAI({ apiKey: config.apiKey, baseURL: config.endpoint, dangerouslyAllowBrowser: isBrowser });
```

### P2 —— 双入口与构建

5. 新建 **`src/lib-browser.ts`**，导出纯函数侧 API：`resolveConfig`、`loadDefaultConfig`、`generateCommitMessage`、`generateCommitMessageBatched`、`validateCommitMessage`、`GrcError` / `GrcErrorCode`、`setLogLevel` / `setLogSink`、`setProgressSink` / `getProgressSink` 及公共类型。其 import 图中不允许出现任何 Node 内置模块。
6. **`src/lib.ts` 与 `src/cli.ts`** 两个 Node 入口在加载时调用 `setupNodeGitExecutor()`（位于 `src/node/setup.ts`）装配默认执行器，公开导出不变。装配逻辑收敛到单一函数，避免两处直接 `setGitExecutor(childProcessExecutor)` 漂移——历史上 CLI 入口漏装导致「git 执行器未装配」报错，详见 S07 §3 强制约定 E1。浏览器 / WebView 入口 `lib-browser.ts` 不装配，由调用方经 `setGitExecutor` 注入。
7. 新建 **`vite.browser.config.ts`**：entry 指向 `src/lib-browser.ts`，`formats: ["es"]`，`emptyOutDir: false`（照 `vite.cli.config.ts` 的套路，避免清掉库产物），`external` 只留 `openai`，产物进 `dist/browser/`。
8. **`package.json`**：`exports` 增加子路径；`build` script 串上新构建。类型声明无需额外配置——`tsconfig.build.json` 的 `include` 是 `src/**/*`，`dist/types/lib-browser.d.ts` 会自动产出。

```json
"exports": {
  ".": { "types": "./dist/types/lib.d.ts", "import": "./dist/index.js", "require": "./dist/index.cjs" },
  "./browser": { "types": "./dist/types/lib-browser.d.ts", "import": "./dist/browser/index.js" }
}
```

### P3 —— 防回归护栏

9. 新增冒烟脚本（如 `scripts/check-browser-entry.mjs`，挂到 `npm run build` 之后）：
   - 对 `dist/browser/` 产物 grep `child_process` / `from "fs"` 等字样，命中即失败；
   - 在 Node 里 import 浏览器产物，验证 `resolveConfig` / `validateCommitMessage` 可调用、git 相关符号不存在或抛带 `code` 的 `GrcError`。

### 接线示例

Tauri WebView（diff 由 Rust 侧算好传入）：

```ts
import { generateCommitMessage, resolveConfig } from "git-repo-comitter/browser";
import { Command } from "@tauri-apps/plugin-shell";

const output = await Command.create("git", ["diff", "--cached", "-c", "core.quotepath=false"], { cwd: repoPath }).execute();
const config = resolveConfig({ apiKey, endpoint, llm: { model: "deepseek-v4-flash" } });
const message = await generateCommitMessage(output.stdout, config);
// 回填输入框，交给用户修改
```

Next.js client component（BYOK）：

```tsx
"use client";
import { generateCommitMessage, resolveConfig } from "git-repo-comitter/browser";

const config = resolveConfig({ apiKey: localStorage.getItem("llm_key") ?? "", endpoint });
const message = await generateCommitMessage(diffFromServerAction, config);
```

## 风险

| 编号 | 级别 | 风险 | 处置 |
|---|---|---|---|
| R1 | 🟡 | CORS：浏览器直连自定义 `endpoint` 不保证放行（`api.openai.com` / DeepSeek 均返回 `Access-Control-Allow-Origin: *`，实测可用） | 不通时走 Tauri Rust 代理或 Next 服务端代理，库无需改动 |
| R2 | ⚪ | openai SDK 进入浏览器包，体积约两三百 KB | 可接受；介意时按 D2 换 fetch transport，单点替换 |
| R3 | ⚪ | `execGit` 未装配时若静默失败会掩盖问题 | P1.3 已设计为抛 `GrcError(GIT_FAILED)`，不静默 |

## 明确不做

- **不引入 isomorphic-git**：放弃原生 git 语义（复杂 diff、`--numstat -z` 细节）换取纯 JS 执行，收益不抵成本；
- **不给 CLI 加 `--generate-only`**：库 API（`generateCommitMessage(diff, config)`）已精确覆盖「只生成不提交」场景，CLI 的自动 `git add` + 交互问答与目标场景本就是两回事；
- **不做 WebView 内直接调 git（Tier 2）**：需把 `GitExecutor` 全链 async 化，动 F05 公开契约，留待 v2 单独评估。

## 开放问题

1. 浏览器产物是否也需要 CJS 格式？倾向仅 ESM（现代打包器通用）。
2. 浏览器端配置持久化由谁负责：调用方自管（localStorage），还是库提供 `ConfigStore` 端口注入？当前设计倾向前者，库不越界。
3. D2 的 fetch transport 替换是否提前到本期，还是等 bundle 体积成为实际问题再动？
4. Tier 2（WebView 内 git 注入）是否排入 v2？

## 结论

浏览器适配的本质不是「给 WebView 打补丁」，而是把既有的 4 个环境接入点收敛到端口后面，再补一个浏览器入口。纯核（prompts、校验、生成、分批、预算、重试）已就绪且零污染，改造是机械改动：**P1 半天，P1+P2 一天内可完成并验证**。收益是同一套代码同时服务 Node CLI、Tauri WebView、Next.js 浏览器端三个场景，且 `.` 入口的既有契约零变化。

实施后需同步更新 [S01.项目结构](../spec/S01.项目结构.md) 第 6 节「双入口」表与第 5 节模块职责清单（`config/loader.ts`、`infra/git/runner.ts` 两行职责描述变化）。
